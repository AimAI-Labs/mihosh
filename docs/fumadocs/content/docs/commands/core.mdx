## First use

Run `mihosh` and open **Core** in the navigation bar. The application works without an installed core or a subscription.

On first use, select **Set up and start** and press `Enter` to install the bundled verified version, create a DIRECT configuration and start the core. Then open the Sub page to add a subscription URL or a local Mihomo configuration.

The baseline configuration provides direct connections, not proxy nodes. System proxy settings, shell environment variables and TUN are separate facilities; starting the core does not route every application's traffic through it.

## Core menu

| Key | Action |

| `←` / `→` or `1` / `2` / `3` / `4` | Switch Everyday, Versions, Advanced and GEO sections |

| `e` | Edit download proxy and accelerator settings |
| `h` | Install, control and configure automatic startup of the background service |
| `y` / `n` | Toggle system proxy / TUN |
| `c` | Recover network settings after an unexpected exit |
| `p` | Change managed ports after stopping the core |

Actions are grouped into Everyday, Versions, Advanced and GEO, each with a short explanation. Click an action to run it. The status panel shows core information; switches show saved preferences, whose effects depend on the running core. Wide terminals use 43% / 57% panels; narrow terminals stack the content. Use `Tab` and `Enter` inside forms. Exiting Mihosh stops the child owned by a session. A background service continues after the TUI exits. Existing external cores remain under their original owner.

## GEO management

Press `4` in Core to inspect the managed core's `Country.mmdb`, `GeoIP.dat`, `GeoSite.dat` and `ASN.mmdb`. The list shows actual filenames, sizes and modification times, or Not downloaded for missing files. Select a file and press `Enter` or click to download or update it through the configured proxy/accelerator chain with SHA-256 verification. Press `z` after updating to restart the core and load the new data.

Existing filename aliases and configured official lite datasets are preserved. Custom sources are marked for management through the core. External cores retain GEO updates in Settings > Mihomo.

## Visual release browser

Press `2` in Core to browse official stable releases. The list matches assets to the current OS and architecture, showing version, publication date, size, and Current / Installed badges. Each on-demand request reads up to 10 upstream releases. Compatible stable entries are appended to one continuous list and deduplicated by tag. Arrow-key and wheel navigation near the bottom automatically load older releases until upstream history ends, skipping fully filtered batches. Loaded records live in a session temporary directory, with a fixed 64-record memory cache and rendering limited to visible rows. All loaded history remains browsable; exiting the app cleans up the temporary directory.

Select with the arrow keys or mouse to inspect the matching asset. **Selecting or downloading a release does not switch or restart the running core.** Press `Enter` / `i` to download, then explicitly press `a` to activate an installed version, which may restart a managed core. The current version is not activated again.

Use `PgUp` / `PgDn` or `[` / `]` to move through the continuous list. `End` moves to its loaded end and triggers another load, also available through Load more. The footer shows the loaded count, loading status, or completion. `r` / `v` refresh from the latest releases and replace the old snapshot only after success; `t` finds a stable version directly. Failed loads retain all displayed data and pause automatic requests; press `r` or click Retry to resume the failed batch. An initial failure leaves the bundled verified release or the existing single-release cache available, explicitly labelled as fallback data. Downloads without trusted SHA-256 metadata are disabled. Retry through direct/proxy access, or use `l` to import an independently verified local executable.

The interaction draws on the list, status chips and separate action buttons in [Clash Verge Rev's core manager](https://github.com/clash-verge-rev/clash-verge-rev/blob/dev/src/components/setting/mods/clash-core-viewer.tsx), extended here to lazily browse all compatible stable release history. Metadata uses the [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#list-releases), retaining Mihosh's download fallback, source restrictions and checksum verification.

## CLI

```bash
# Install the verified version and save a baseline configuration without starting it
mihosh setup --output json

# Run in the foreground; another terminal can control that managed session
mihosh core start
mihosh core status --output json
mihosh core restart --output table
mihosh core stop --output plain

# Query, install and select stable versions
mihosh core releases --output table
mihosh core install --version v1.19.33 --output json
mihosh core activate --version v1.19.33 --output json
mihosh core upgrade --output json
mihosh core rollback --output json
```

Without `--version`, `core install` uses the application's verified release record. An explicit tag queries official release metadata. Installation and activation are separate operations, and external installations are not overwritten.

Local import expects an **extracted executable** and its independently verified SHA-256. An archive's digest cannot verify the extracted file.

```bash
mihosh core import --file /path/to/mihomo --version v1.19.33 --sha256 "YOUR_VERIFIED_SHA256" --output json
mihosh core configure --output json
```

`setup` and every `core` subcommand support `--output plain|table|json`. Foreground `start` returns its final result after stopping or interruption. Ending the owning foreground command stops its child. In service mode, `start` returns when the background core is ready.

## Background services and automatic startup

Press `h` in Core, select **Install background service** with the arrow keys and press `Enter`. Press `Esc` to return. Stop a session core before installing its background service. Installation copies Mihosh into `~/.mihosh/bin/` as a stable service entry and selects `core.runtime: service`. Core start/stop/restart then control that service. Closing the TUI leaves it running; profile activation and version changes are forwarded to its private owner endpoint.

```bash
mihosh core service install --output json
mihosh core service enable --output json
mihosh core start --output json
mihosh core service status --output json
mihosh core service boot --output json
mihosh core service disable --output json
mihosh core service uninstall --output json
```

Linux uses a systemd **user service**. `enable` starts it on login. `boot` additionally invokes `loginctl enable-linger`, which may require authorization. Uninstall removes only the owned unit and retains data; it leaves user lingering unchanged to protect other services. Restart attempts are bounded. Core logs go to the user journal, available through `mihosh service logs`.

After updating Mihosh itself, stop and reinstall the stable service entry. Legacy `mihosh service` commands resolve the managed target when no `--unit` is supplied; explicit units retain their external systemd semantics.

## System proxy, TUN and recovery

```bash
mihosh core system-proxy on --output json
mihosh core system-proxy off --output json
mihosh core tun on --output json
mihosh core tun off --output json
mihosh core network-recover --output json
```

These commands share Core's `y` / `n` / `c` actions and support `--output plain|table|json`. Switches record desired settings; a stopped core does not imply active traffic capture. Running TUN changes validate a candidate and restart under control, restoring the old configuration and preference on failure. Download proxies, shell `on/off`, system proxies and TUN remain separate facilities.

P2/P3 target Linux only. System proxy uses GNOME GSettings with a user D-Bus. Other desktop backends fail before mutation. Prior values are saved and restored only for fields still matching Mihosh's applied values, preserving intervening user changes.

Linux TUN requires `/dev/net/tun`, iproute2 and `CAP_NET_ADMIN` on **the Mihosh coordinator and recovery guard**, not only on the kernel executable. An administrator can explicitly grant capabilities to the installed stable service entry:

```bash
sudo setcap cap_net_admin,cap_net_raw+ep "$HOME/.mihosh/bin/mihosh"
```

For foreground use, grant them to the actual Mihosh executable. Recheck capabilities after updates or copying binaries. No silent elevation occurs.

Managed TUN reserves its own interface name, routing table and rule range after checking collisions. It uses the system stack, automatic routing/interface detection, and no additional auto-redirect or strict firewall rules. DNS has no external listener; existing nameservers are retained, or Cloudflare/Alibaba DoH and bootstrap DNS are generated. Interface DNS state is restored with the owned TUN resources.

`runtime/network-recovery.json` records recovery data before network mutation; `network-change.json` also protects interrupted TUN configuration changes. An independent guard restores proxy fields and cleans owned TUN resources after owner exit. Under systemd it lives in a separate transient user unit. Failures retain the journal for retry. `network-recover` requires ownership locks to prove that no active owner exists; it never adopts another core or removes unrelated interfaces. Status includes runtime, automatic startup, desired proxy/TUN switches and pending recovery.

## Native verification

Regular `go test ./...` never mutates real system services or desktop proxies. `scripts/test-managed-core-linux.sh` accepts `isolated`, `service`, `tun` or `proxy`, followed by verified local kernel and Mihosh paths. TUN tests create their test uplink in a separate user/network namespace. Native desktop proxy tests require `MIHOSH_ALLOW_NETWORK_CHANGES=1`.

`scripts/test-managed-core-container.sh` provides an isolated Linux environment with TUN, D-Bus and GNOME settings. It mounts no host directories and publishes no ports. The container is removed after testing unless `--keep` is supplied. Run `test-managed-core-linux.sh service` separately for native systemd lifecycle coverage: it creates only an independently named temporary unit with a 256 MiB memory limit and no system proxy or TUN. Actual results are recorded in the proposal.

## Download fallback and verification

Release queries and asset downloads independently try **official direct access → available HTTP(S) proxies → GitHub accelerators**. The proxy stage is skipped when none is available. Direct and accelerator requests explicitly bypass environment proxies. The proxy stage considers configured, applicable environment and node-capable managed proxies in that order; environment proxies honor `NO_PROXY`.

Built-in endpoints are `https://gh-proxy.org/` and its same-service compatibility endpoint `https://gh-proxy.com/`. Use `e` in Core to reorder or add endpoints, or leave the list empty to disable them. Advanced capability settings are available in application configuration:

```yaml
core:
  proxy: ""
  download_timeout_seconds: 600
  accelerators:
    - url: https://gh-proxy.org/
      metadata: true
      asset: true
```

The download task deadline accepts 30–3600 seconds; `0` uses 600 seconds, and route deadlines scale with that budget. Omitting `accelerators` uses the defaults; `accelerators: []` disables them. Set `metadata: false` for asset-only endpoints.

Accelerators carry public GitHub resources. They do not receive subscription addresses, controller secrets or GitHub Tokens. Gateway metadata cannot establish asset authenticity: installation still requires an embedded official digest or a valid digest obtained through official direct/proxy access. Missing trusted digests cause installation to fail.

Downloads have task and route deadlines, one bounded retry and progress reporting. Changing routes starts a fresh download. Unverified `.part` files cannot replace an installed version. Retry failed third-party endpoints, change network settings or import a local executable.

## Ownership and files

Managed versions live in `~/.mihosh/core/versions/<tag>/`; runtime configuration is in `~/.mihosh/runtime/`. Installation records include source URLs, hashes and upstream source/license links. Application `core` settings choose mode and version; controller credentials and proxy ports come from `runtime/config.yaml`. `MIHOSH_CONFIG_DIR` selects an absolute data root, fixed through the service entry’s `--home`; configuration, profiles and backups share that root.

External API connections retain their original installation method. Explicit external connections have no implicit local file binding and cannot write a default local Mihomo configuration.

Profile activation validates a candidate before applying it and restores the previous configuration and active profile on failure. Managed imports preserve local controller and proxy settings, apply the explicit Core TUN choice and remove additional subscription-provided listeners. Imported data cannot enable TUN by itself. Interrupted version changes and configuration transactions are recovered during startup.

Asset selection covers Linux/Windows amd64 compatible and arm64. Linux amd64 has real-core integration coverage; see implementation records in the proposal for build and runtime verification of other targets.
